# Loom 实现决策

## 单用户与应用内日历

初赛主流程管理单设备上的一个目标日历。用户提交目标与截止日期，模型拆分任务并生成每日安排，用户通过文字建议修改并确认计划。

## 规划由宿主模型完成

客户端通过宿主能力 `model.complete` 完成规划：拆分任务与排程分两次调用，各自带必填 JSON Schema；约束核验未通过时把违规码送回模型修正一次，仍不通过则进入可重试的失败态。执行与核验不经过模型，模型只写理解和方案。拆分输出可附里程碑与追问，排程输出可附安排理由与风险，均经 Schema 约束并展示在界面。宿主没有注册模型服务时，客户端自动进入演示模式，使用内置固化数据走完全相同的应用与核验路径。

## 空闲时段由客户端预计算

排程输入携带客户端本地计算的未来 14 天空闲时段列表（扣除固定事件与已完成、已开始块），模型直接从中选择拼装时间块，避免自行推算星期与空闲时间；时段列表仅供参考，约束判定仍以客户端 C1–C7 核验为准。

## 确认与本地核验

候选计划需要符合完整日历约束。客户端确认时检查版本与原始时间块，将完整候选内容保存后实际回读，由客户端本地的 `verify_calendar_reasons` 比较任务、安排和约束，形成核验回执。通过核验后更新正式计划。正式与候选计划分别保存，支持切换查看和重新启动恢复。用户在当天安排中把时间块标记为完成是本地业务提交：扣减剩余工时、推进项目版本、重算容量并双快照保存，不经过模型；随后可发起 progress 重排，由模型只为未完成任务安排未来时间块，已完成与已开始块由约束 C1 锁定，重走候选确认与本地核验链路。

## 官方宿主与本地存储

原生宿主由 `native/LOCK.json` 固定的官方 OctoSense-App-Hub 提交及其 `Cargo.toml` 引用的 Makepad 与 Octoscript 构建，不使用私有原生改动。客户端保存、草稿、恢复和核验回读全部使用官方 `fs` 文件能力，不依赖自定义宿主服务。业务记录在应用目录交替写入 `state-a.json` 与 `state-b.json` 两份完整快照，写入后回读比较，失败即停止当前操作。

## 进度与时间

剩余工时表示当前时间之后需要安排的小时数。已经开始或完成的时间块保留原始事实。客户端固定东八区（UTC+8），项目使用该时区的无偏移日历时间；不读取设备时区文件，也不需要处理夏令时。

## 零服务化与预算

客户端清单只声明 `storage` 与 `model` 两项能力，不声明网络，没有自有服务端，也不需要保持任何本机服务运行。单次 `model.complete` 的指令预算、频率与输出体积由宿主强制执行；客户端只对 `task`/`input`/`schema` 做字段裁剪。模型调用失败全部显示为可重试的失败态，宿主没有模型服务时进入演示模式。

## 客户端入口

`bundle/main.splash` 是客户端唯一入口，使用 Figma 的顶部品牌、目标输入、月历、当天安排与右侧计划说明。真实月份与日期使用 OctoScript 日历能力生成；任务安排来自宿主模型返回或演示固化数据。本地记录在 `state-a.json` 与 `state-b.json` 间交替保存，写入后立即回读比较。
