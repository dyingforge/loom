# 02 探针报告：MiniMax 工具调用与排程收敛

报告日期：2026-10-01。脚本：`scripts/probe_minimax_scheduling.py`。
运行方式：每次使用 `MINIMAX_API_KEY` 真实调用 `https://api.minimax.chat/v1/text/chatcompletion_v2`，
模型 `MiniMax-M2.7`，最多 4 轮，每轮把 `server/domain/constraints.validate` 的违规明细反馈给模型。

## 基准（10 次运行）

| 指标 | 值 |
| --- | --- |
| 总数 | 10 |
| 最终通过（≤ 4 轮内通过） | 10 |
| 最终通过率 | 1.000 |
| 首次通过率 | 0.000 |
| 平均校验轮数（含通过） | 2.40 |
| 中位校验轮数 | 2.0 |
| 平均 token 总用量 | 6232.4 |
| 平均耗时 | 约 80s |

每条原始数据：`scripts/probe_minimax_scheduling.py` + `.scratch/probe02.json`。

## 主要观察

- 模型对 `restDays` 的处理不稳定：第一轮普遍把块排到了周六（Python weekday=5）或跨休息日。
- 给到具体 `[{code, blockId, detail}]` 后，模型在第二轮几乎都能纠正。
- 没有出现 4 轮内不收敛的情况；平均 2.4 轮达标。
- 校验反馈中的 `C5`、`C4`、`C6` 一次性给出后，模型能准确识别并调整切分。
- 唯一一次失败-失败-通过发生在 run 6（4 轮）：模型前两轮都把 t2 排到休息日，第 3 轮又触发 C4 依赖违规，第 4 轮才收敛。

## 决策

- MiniMax `MiniMax-M2.7` 满足 PRD 与探针要求：能调用工具、能理解校验反馈、能修正候选。
- 校验计数（每候选 4 次）的硬上限在 10 次运行中未被触达（最多 4 轮），但仍保留作为停止条件。
- 9 次平均 2 轮收敛意味着用户体验上不会频繁出现“来回改”。
- 未观察到模型拒绝、API 鉴权失败、额度耗尽。

## 风险与遗留

- 探针只覆盖“单文件所有任务、零固定日程、零已完成块”的最简场景；多约束同时失败或更复杂依赖的回归见 issue 19。
- 探针脚本是同步阻塞，单次调用最长约 130 秒；HTTP 适配层把超时设为 30 秒与 PRD 一致，可能在首次调用耗时 > 30 秒时超时。`server/adapters/minimax.py` 通过捕获 `URLError` 返回 `{"type": "failed", "reason": "network: ..."}` 由循环停止，不假装成功。
