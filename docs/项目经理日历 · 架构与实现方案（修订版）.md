# 《项目经理日历》架构与实现方案（修订版）

> 修订说明：①删除时区相关设计，统一使用设备本地时间；②排程由"确定性算法"改为"模型提出方案、程序校验硬约束"；③补齐审查中发现的缺口。标注【新增】或【修改】的为本次变动，标注【默认】的是我替你选的值，可自行调整。

## 一、目标与首版边界

构建一个可以真实运行的项目规划 Agent：理解目标，参考任务依赖和实际进度安排日历，在延误后提出或执行重排，并核验结果。

首版采用 **OctoScript 客户端＋Python Agent 服务端＋MiniMax API**，以符合 OctoSense 独立应用发布要求为目标。Rinx 不作为依赖。**比赛资格需在写代码前核实**，若与"客户端＋自建服务端"形态冲突，须先改架构。

已确定的范围：

- 单用户、单设备，使用应用内日历；固定日程由用户录入。
- 时间一律按设备本地时间处理；首版不处理时区切换与夏令时。【修改】
- 项目、日历、授权和变更记录以本地存储为准。
- 用户操作触发 Agent，不实现后台自动触发。
- 自动调整默认开启，用户可关闭；只自动移动用户明确标记为可调整的任务。
- Agent 可以把一个任务切成多个明确时长的时间块；这些块共享任务进度与完成标准。
- 临时模拟模型只用于跑通第一条完整循环，随后立即接真实模型并删除模拟实现。

## 二、四部分架构

### 1. 大脑：理解与决策

首个接入模型暂定 `MiniMax-M2.7`，模型名与服务地址由服务端配置，DeepSeek 作为后续可切换的提供方。

模型负责：

- 根据目标提出任务、预计工时、依赖和完成标准。
- **提出具体排程**：决定每个时间块放在哪天哪个时段，并结合用户偏好（如"上午做需要专注的任务""留缓冲""少跨天打断"）说明取舍。【修改】
- 提出时间块切分，例如同一任务分成两个一小时块。
- 根据校验器反馈修正排程，直到通过校验或确认无解。【新增】
- 缺少关键条件时询问用户；无法在约束内排下时，提出切分或取舍方案。
- 解释调整原因、影响和可选取舍。

Python 中设置一个薄的模型适配层，保留提供方要求的完整工具调用上下文（如推理内容）。不自动跨提供方降级。[MiniMax 接口说明](https://platform.minimax.io/docs/api-reference/text-openai-api)

**模型输出是建议；任务状态、操作权限和执行成功与否，都以程序记录及工具结果为准。排程"好不好"由模型判断，"合不合规"由程序判断。**【修改】

### 2. 记忆：事实、历史与本轮上下文

| 记忆 | 内容 | 存放位置 |
| --- | --- | --- |
| 项目事实 | 目标、截止日、里程碑、任务、依赖、剩余工时、日历、授权、用户偏好 | 应用本地 |
| 变更记录 | 方案、调整前后差异、批准内容、执行和核验结果 | 应用本地 |
| 本轮上下文 | 请求、模型工具调用、工具返回、暂停位置 | 运行时；暂停时保存在本地 |

**进度口径**【新增】：以任务为单位记录"完成状态＋预计剩余工时"，由用户更新，是唯一依据。时间块只记录"已完成/未完成"；块被标记完成时，客户端提示用户更新剩余工时，但不自动扣减，也不从已用时间或聊天历史推断。两者不一致时以任务的剩余工时为准，排程工具据此检查切分总量。

**项目版本**：每次修改项目版本加一（**撤销也算一次修改**）。方案绑定生成时的版本，执行前发现版本变化就重新计算，**最多自动重算 1 次**，仍变化则暂停并提示用户。【默认】

**服务端数据**：按次接收必要快照，默认不长期保存项目内容；运行日志只记录请求编号、耗时、用量和错误类型。模型提供方会收到规划所需内容（包括任务标题等用户文本），写入隐私说明。用户文本可能含注入指令，但权限与硬约束由程序强制，模型无法绕过，这一点写入安全说明。

**本地存储**【修改】：采用两个交替写入的完整快照文件（A/B）。每个快照包含**递增序号和校验值**，且把日历、变更记录、项目版本放在**同一个快照内一次写入**，避免多文件写到一半失败。写入后读取检查；启动时读取两个文件，丢弃校验失败者，取序号最大的有效快照。不依赖脚本 API 未提供的文件重命名操作。

### 3. 工具：校验与执行

**Python 服务提供**：

- **读取项目快照**：本轮统一的数据来源。
- **检查任务结构**：依赖循环、缺失任务、工时和切分总量。
- **分析延误影响**：后续依赖、剩余容量、里程碑风险。
- **查询可用时段**：返回指定范围内扣除固定日程、已完成块和休息日后的空闲时段，供模型选位。【新增】
- **校验候选排程**：模型提交一版候选排程，校验器逐条检查硬约束，返回通过或具体违规明细（哪个块、违反哪一条）。校验器**只判断、不替模型排**。【修改，取代原"计算候选排程"】
- **生成变更方案**：对通过校验的候选，输出变更差异、风险和需要批准的例外。
- **核验执行结果**：比较客户端回读结果与批准方案。

**OctoScript 客户端提供**：

- 保存进度、权限、偏好和工作时段。
- 执行前**独立复核硬约束**：版本一致、授权满足、不移动固定日程和已完成块、不越工作时段、不违反依赖。这套检查与服务端校验器逻辑相同但分别实现，服务端出错时客户端不会照单执行。【新增】
- 保存日历并回读真实结果。
- 撤销最近一次日历变更，并保留撤销记录。

**撤销规则**【新增】：撤销只恢复日历安排，不覆盖之后录入的实际进度；撤销生成新的项目版本和变更记录；仅支持撤销最近一次，撤销后不可再"重做"；若旧安排已违反当前约束（如依赖或进度已变），拒绝撤销并提示重新规划；撤销时作废所有绑定旧版本的待确认方案。

### 4. 循环：管理继续、暂停和结束

用普通 Python 函数实现循环，让每个步骤都能直接阅读和调试：

1. 用户提交目标、更新进度或新增事项。
2. 客户端发送项目快照与触发原因。
3. 模型选择工具，程序校验参数并执行。
4. 工具结果返回模型，必要时继续调用。
5. 模型提交候选排程，校验器反馈；不通过则模型修正后重新提交。
6. 通过校验后生成结构化调整方案，程序检查权限与风险。
7. 符合自动调整条件时执行；否则保存为待确认并暂停。
8. 客户端保存日历并回读，将结果交回服务端。
9. 核验通过后标记"已核验"，记录结果并结束。

**上限与停止条件**【修改，写死数字，均为【默认】】：

- 每轮最多 **10 次**模型调用。
- 同一候选排程最多提交校验 **4 次**；4 次仍不通过，模型须改为提出切分或取舍方案，或明确报告无解。
- 同类无效工具参数连续出现 **2 次**即停止。
- 单次模型调用超时 **30 秒**，不自动重试；用户可手动重试。
- 任何停止都展示原因。**模型失败或排不出方案时，不返回预设答案，不退回到隐藏的固定算法，也不会标记成功。**

学习用的运行记录（轨迹面板）展示工具名称、参数、结果、每次校验的违规明细、权限判定和暂停原因。**它是本项目最重要的演示资产，赶工时不删。**

## 三、排程、权限与接口

### 排程规则【修改】

**硬约束**（由校验器和客户端强制，违反即不可执行）：

- 工作时段、休息日由用户设置。
- 已完成时间块和已发生的工作不移动。
- 固定日程不可被占用。
- 依赖顺序必须满足（后继块不早于前驱完成）。
- 每个任务的时间块总时长等于其剩余工时（切分总量检查）。
- 每个时间块是连续的一段，且完整落在一个工作时段内。

**软偏好**（由模型权衡，不强制，但须在方案中说明取舍）：

- 优先级高者先排，同优先级尽量保持原计划顺序。
- 尽量少改动：延误重排只处理变化任务及受影响的后续任务，其余时间块原则上保留。
- 用户偏好：专注时段、缓冲、减少碎片化、避免临近截止日才完成等。
- 软偏好之间冲突时，模型选择并解释，不要求结果唯一或可复现；同一输入多次运行可有不同但同样合规的方案。

**无法排入时**：校验器返回未满足的约束与缺口，由模型提出新的切分或取舍方案（例如延期某任务、缩小范围），交用户决定。工时估计和切分建议在首次计划中展示给用户确认。

### 自动调整边界

只有同时满足以下条件才能自动执行：

- 自动调整开关开启。
- 所有被移动任务均由用户标记为可调整。
- 不移动固定日程，不越过工作时段。
- 不违反依赖，不引入或加重里程碑、截止日风险。
- 项目版本与方案版本一致。

移动固定日程、越过下班边界或涉及截止日风险时，先展示具体影响。用户批准仅适用于当前方案，不永久扩大权限，也不隐式修改截止日。**确认按钮提交后进入"处理中"状态，防止重复点击。**【新增】

"建议、待确认、已更新、已核验"分别表示方案已生成、等待决定、数据已保存、回读检查通过。\*\*"已核验"仅表示保存结果与批准方案一致，不代表第三方证明或方案最优；\*\*核验结果仍需保留用户接受的延期或其他例外。【新增】

**标记入口**【新增】：任务卡片上提供一步可达的"可调整"开关，演示数据预先标好，避免自动调整永远不触发。

### 最小接口

Python 服务提供两个接口：

- **推进 Agent**：接收项目快照、触发事件及可选的本轮上下文，返回澄清请求、调整方案或失败原因。
- **核验执行结果**：接收批准方案、执行前后版本和回读快照，返回检查结果。

通过结构化类型表达项目、任务、时间块、调整方案和执行回执。工具参数与模型输出统一校验；客户端执行前再次检查版本和权限。

## 四、按学习顺序实现与验收

### 阶段 0：技术探针（第 1 天，先于一切）【新增】

用最小代码验证，任一项失败就先调整方案：

- 比赛资格与"自建服务端"形态是否兼容。
- OctoScript 能否访问你的公网 HTTPS 服务；`storage` 的读写与大小限制；文件操作的实际限制。
- MiniMax-M2.7 的模型名、可用性、工具调用的稳定性，以及完整上下文（含推理内容）回传是否按文档工作。
- 模型能否在校验器反馈下收敛出合规排程（用 3 个任务试 10 次，记录一次通过率与平均校验轮数）。这项决定"模型排程"的可行性。

### 阶段 1：工具与最小循环

先建立最小 OctoScript 页面、Python 服务、三任务数据，以及**校验器与可用时段查询**这两个真实工具。

临时模拟模型沿同一调用接口，提交一版**写死的候选排程**走完：

**读取项目→分析延误→提交候选并校验→等待确认→客户端保存→回读核验。**

验收：计划确实改变，重开应用可以恢复，变更记录可查，撤销可用。此阶段不等待完整界面完成。

### 阶段 2：立即接入真实大脑

接入 MiniMax，删除模拟模型、预设模型回复及切换开关。

验收：

- 模型实际发出工具调用，并使用返回结果继续决策。
- **模型自己提出排程，校验器能拦截违规方案，模型能依据违规明细修正。**【新增】
- 改变任务工时、依赖或用户偏好，结果随输入变化。
- 缺少关键条件时询问用户；排不下时提出切分或取舍。
- API 失败、参数错误、校验反复不过和达到循环上限时，明确停止。

### 阶段 3：完成日历与权限体验

完善目标输入、任务和切分建议、日历、进度更新、方案差异、确认、核验状态与撤销入口。

三任务演示准备两种延误：

- **可吸收的延误**：只移动已授权任务，在工作时段内自动完成重排。
- **影响截止日的延误**：指出后续任务和里程碑风险，等待用户明确批准后更新，保留风险提示。

同时检查固定日程冲突、依赖循环、确认期间项目变化、重复点击确认、保存失败、重启恢复和撤销。

**范围取舍**【新增】：

- 必须保留：两种延误场景、批准流程、回读核验、撤销、轨迹面板。
- 可简化：离线模式只做只读查看并允许记录进度；"重复点击"用状态位处理。
- 可推迟：多提供方切换、更完整的日历界面、发布材料之外的打磨。

### 阶段 4：发布准备

在真实运行环境中完成交互验证、截图和应用包检查，准备发布材料。通过本地检查与获准上架分别记录。

**演示备份**：提前录制一段真实运行的完整录屏。演示当天若 API 失败，如实说明并播放录屏，不使用预设答案冒充成功。

## 五、固定测试场景（兼作演示脚本）【新增】

| 场景 | 预期状态走向 |
| --- | --- |
| 可吸收延误 | 建议 → 已更新 → 已核验（自动执行） |
| 影响截止日的延误 | 建议 → 待确认 → 用户批准 → 已更新 → 已核验，保留风险提示 |
| 依赖循环 | 检查任务结构报错，要求用户修正，不进入排程 |
| 缺少关键信息 | 模型提问，暂停等待回答 |
| 排不下 | 校验器报缺口，模型提出切分或取舍，待确认 |
| 模型提交违规排程 | 校验器拦截，模型修正后通过（轨迹面板可见） |
| 确认期间版本变化 | 自动重算 1 次；仍变化则暂停提示 |
| 保存失败 | 不标记已更新，保留待确认，提示重试 |
| API 失败 | 明确停止，不返回预设答案 |

## 六、发布与服务端约束

- 应用声明实际使用的 `storage`、`net` 和服务端主机。
- 客户端通过已声明的公共 HTTPS 入口访问服务；不默认直连本地 HTTP 后端。
- 模型密钥只保存在服务端，应用包不包含密钥、令牌或登录表单。
- 服务端独立部署，不装入 OctoScript 应用包。
- 首版不增加云端账户。因无令牌的公网接口易被滥用，服务端**必须**做：按 IP 限流、每日费用上限，并预留一个仅评审使用的演示额度（如独立的口令或额度池），避免限额被刷光导致演示当天不可用。【新增】
- 离线时仍可查看本地计划和记录进度；依赖模型的规划明确显示暂不可用。
- 发布描述写明远程处理的数据、已验证的平台和能力，不宣称已实现宿主 Agent 或后台自动运行。

这些选择依据仓库的[应用规则](https://github.com/OctoSense-org/OctoScript-App-Design-Flow/blob/main/AGENTS.md)、[网络与存储 API](https://github.com/OctoSense-org/OctoScript-App-Design-Flow/blob/main/docs/SCRIPT-API.md)及[发布流程](https://github.com/OctoSense-org/OctoScript-App-Design-Flow/blob/main/docs/PUBLISHING.md)。正式发布前重新核对版本与要求。
